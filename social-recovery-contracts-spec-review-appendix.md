## Front B — SDK surface fit (B1–B20)

**B1 | INCONSISTENCY | blocker.** THEIRS: chain storage is one salted commitment plus the wait; "the contract itself learns the rule only when a request reveals it at recovery" (design.md:273-275, 283-285; I-15 invariants.yaml:179-188); readable config "lives with the holder and their backup" (design.md:198). OURS: `getRecoveryConfig(account) → {path, waitingPeriod}` serving B-01, C-01, D-04, G-01. IMPACT: at the private default with no local copy, `path` is unavailable; G-01, D-04 and the edit builder are unbuildable from this call. FIX: split into `getRecoveryStatus(account) → {configured, waitingPeriod, setupNonce, commitment, privacyLevel}` (chain-only) and `resolveConfig(account, {password?, localPath?}) → RecoveryPath | 'hidden'`.

**B2 | INCONSISTENCY | blocker.** THEIRS: the backup rides the setup event — `event SetupCommitted(setup, wait, metadata, backup)`, `backup = encrypt(password_key, config) | config | empty` (design.md:288-293). OURS: `prepareSetup(account, path, waitingPeriod)`; encryption is a separate later call. IMPACT: password, privacy level, salts, adapter and repayment knob are all inputs to the same setup transaction; our signature omits all five and the wizard has no privacy-dial screen. FIX: `prepareSetup(account, path, waitingPeriod, {privacyLevel, password?, adapter, repayment?})`; add a privacy-dial + password-minting step to Flow C.

**B3 | INCONSISTENCY | blocker.** THEIRS: without the backup a fresh device "cannot even begin a recovery" (design.md:293); "the setup wizard never mints a password … so the card as specified cannot start a recovery" (ux-flows-discrepancies.md:26). OURS: §2.6 "wrong password never blocks recovery (48/56)"; "a failed decrypt degrades to hidden values, never to an error that stops the flow". IMPACT: at the encrypted level, no password = no rule, no salts, no cleartext configs — recovery impossible, not degraded. FIX: mandate the cleartext level for MVP, or retire 48/56 and replace with "password lost = configuration lost".

**B4 | INCONSISTENCY | blocker.** THEIRS: each account implementation needs a thin adapter committed inside the setup commitment, "the Ambire fork the demo integrates being the one adapter this engagement owes" (design.md:203); Q-19 still assumes an Ambire-fork account (open-questions.yaml:93-98). OURS: A5 "a bare-bones 4337 implementation, not the Ambire account stack"; extension item 1. FIX: ask them to scope a generic 7579 adapter; tell them Q-19's premise is stale.

**B5 | INCONSISTENCY | major.** THEIRS: executor coupling; "proof verification cannot run in the validation phase, so the submission is a plain call or a call inside some funded party's own operation either way" (tradeoffs:76; design.md:244-260). OURS: A5 "validated by the account/module and the submission rides as a UserOperation"; `PreparedTx{kind:'userop', sponsored}`. IMPACT: a sponsored UserOp's sender is a third party's account, never the recovered one; extension item 3's paymaster wiring targets the wrong sender. FIX: rewrite A5's second clause; make PreparedTx express "inner call for a third-party submitter" as a first-class kind.

**B6 | ANSWERS | major.** THEIRS: Q-5 — EF "ranks sponsorship a product improvement rather than a demo requirement and rules out any kit-run relayer, so the demo carries no named payer"; "a sponsor cannot rate-limit by identity, only simulate … simulation filters an invalid request but never a race". OURS: §5.2. FIX: mark answered-negative; self-pay primary for MVP.

**B7 | INCONSISTENCY | blocker.** THEIRS: binding digest = `chain_id, account, recovery_contract, version, setup_nonce, keccak256(rule), attempt_id, purpose, valid_until, slot, keccak256(handover)` (design.md:155-171). OURS: `RecoveryIntent{account,newOwner,nonce}`. IMPACT: three of eleven inputs; every claim fails verification. `handover = (new_key, old_authority, install_path)` — newOwner alone lets the submitter choose the rest (design.md:148). FIX: replace RecoveryIntent with the full digest input; SDK derives setup_nonce and the predicted attempt_id from chain reads.

**B8 | INCONSISTENCY | major.** THEIRS: I-8a — a set satisfying the rule signed under the CANCEL purpose cancels an attempt (invariants.yaml:102-111); D-6 leans on it for "a keyless holder whose honest side can still satisfy the rule" (design.md:309). **B9 | INCONSISTENCY | major.** THEIRS: one signature fills exactly one slot in one clause (design.md:148); every proof must be inside `valid_until` when the request lands, "so the windows must span the slowest helper" (design.md:124, Q-4). OURS: `Claim{methodId,data,createdAt}`; ProgressReport has no slot or expiry. IMPACT: a helper named in two clauses must sign twice; expired claims silently kill a submission. **B10 | INCONSISTENCY | major.** THEIRS: an attempt is born satisfied — no partial on-chain state (I-9); used credentials readable only from submission calldata (design.md:277, Q-12). **Front B bottom line.** (1) Their design supports our surface's shape but not its signatures — createClaim/buildApprovalPayload carry 3 of 11 digest inputs. (4) Two substrate blockers: no adapter for a bare-bones 4337 account, and sponsorship rides a third party's UserOp. (5) Thirteen items of extension work land on us that are not in the plan.
