Foundations

The model in one minute

An account is protected by exactly one recovery path. The path is required method rows plus ANY-of groups, all combined with AND. Completing it recovers the account after the account's waiting period (48h default, 24h contract floor), during which the current owner can cancel.

recovery path = the account's one AND clause method = one credential waiting period = timelock, one per account path = required rows AND any-of groups ANY-of groups mix methods, M-of-N: passkey AND [Ana OR email]
DecidedOne recovery path per account (decision 73) — the OR-of-paths level is removed. No second path, no “Add recovery path”, no path choice during recovery. The UI keeps the names “recovery path” and “recovery method”.
DecidedUsers see “Account recovery” — “Social Recovery Kit” stays internal.
DecidedFour methods in v1: passkey, guardians, ZK Email, Anon Aadhaar (listed last, badged “India”).
DecidedOne chain per policy; multichain out of scope for v1. Personas ground every choice — persona research.
DecidedAccount context: the recovery module is ERC-7579 on a 4337 smart account — the initiative focuses on 4337, and 7702 support is deferred (decision 78). No user-visible copy changes from this.

Flow C · 1 of 2

Setup — presets first, guidance and power on top

No mode-picker fork. The tab lands on the Presets state with three starter path shapes visible and editable — the user picks one, and it becomes the account's single recovery path. “Guide me” → Express wizard. “Customize” → Advanced builder.

Starter path shapes (48h default, 24h floor)
  • passkey AND [2 of 3](guardians) — “Your device + your guardians”
  • passkey AND zk_email — your device + your email, both required
  • [2 of 3](guardians) — “Guardians only”, no device or platform dependency
Builder rules
  • ANY-of groups are generic: members mix guardians, passkeys, email, Aadhaar; every group has an M-of-N threshold. Guardians are ordinary members.
  • The account's one path = required rows AND groups; a lone group, a single method, and 1-of-1 groups are all valid.
  • Wizard and presets build required rows + at most one group; several groups in one path are Advanced-only. Two-method inventories get one [1 of 2] group.
  • Instance uniqueness: one enrolled instance appears once in the path — never as a required row and a group member at once. Method types may repeat with different values.
  • Passkey enrollment detects synced vs device-bound; warnings adapt.
  • Guardrails: the contract enforces a 24h minimum wait; the builder blocks duplicate instances. Group encoding with the kit team.
DecidedSingle recovery path (decision 73): the setup builds one path — required rows AND any-of groups. Presets are path shapes, not paths to combine; “Add recovery path” is gone.
DecidedOne waiting period per account (decision 74): 48h stays the UI default, and the contract enforces a 24h minimum, so the picker offers nothing below 24h. The dominated-path warning is retired — with one path, domination cannot exist.
DecidedWizard vs Advanced shape (decision 75): the wizard and the presets produce required rows + at most one any-of group; several groups in one path stay Advanced-only. Two-method inventories get one [1 of 2] group.
DecidedInstance uniqueness (decision 76): one enrolled method instance (a specific passkey, guardian address, or email) appears once across the path; the builder blocks the duplicate.
DecidedNo guardian names anywhere — a guardian is an address, shown as blockie + address or ENS. The wallet stores no contact labels; nothing extra to leak (decision 43).
DecidedGuardian checks stay optional — confirmed in the demo-review meeting (decision 52); mutual guardian approval still under consideration.
DecidedThe wizard ends with an optional dry run: rehearse the recovery locally before the save (decision 47).
DecidedSingle-method setups are never forced to add more — the copy recommends a second method, including a second passkey from another device (decision 49).
DecidedThe recovery password gets an explicit, skippable wizard step before the review (decision 48 amended); the card hint is dropped — it could leak configuration. The dry run's recall row covers forgetting. Set once, no change surface, never blocks recovery (decision 56).
DecidedVerify-access scope (decision 54): wizard tests stay blocking; the Advanced builder offers tests without enforcing them.
DecidedAttack-round batch (decisions 58–72): a ten-step wizard map, one status-chip vocabulary, group-as-one-unit progress counting, guardian/member/approval naming, the full threshold-component sweep, error-states-preserve-base, a Back on every step, card & alerts on the management overview, per-request dismissal, shared tx submitting/failed states, display rules, a persistence table.

Flow D · 4 of 4

Recover — what's decided, what blocks it

BlockerFunding & execution. Recovery calls bypass 4337 — no paymaster can sponsor them; no execution relayer exists (backend-zero). The intended UX (sponsored + auto-execute) has no infrastructure owner.
DecidedIdentity confirmation before proof collection; explicit consent screen before the transaction.
DecidedRecovery ends with a required cleanup checklist — the lost device's methods survive rotation and must be replaced. Deferring is allowed; the deferral shows as a flagged banner on the management overview until resolved (decision 46).
DecidedSynced passkeys are flagged too while the lost device stays signed in; the fix includes revoking it from the platform / password manager (decision 50).
DecidedChecklist state persists locally and resumes into a dedicated “Recovery in progress” screen — account, per-row progress, resume/abandon (decision 44). There is no path choice and no “switch path” exit (decision 73): if the path cannot be satisfied, the checklist says so honestly and the partial progress stays until the flow exits.
DecidedOne password name everywhere: "extension password"; "full wallet password" is retired. The recovery password stays a separate, clearly-labeled concept (decision 57).
OpenValue visibility during path display — guardian addresses are natively public today.
Review focus

The identify step assumes the user knows their address or ENS — the personas least likely to know it are exactly the ones recovering. Is the Recovery Card + same-install list enough?

Rollout · decision 79

Milestones — MVP, V1, V2

MVP = one person can protect one account and recover it, with all 4 methods (non-negotiable), preset shapes only. V1 = the guided, confident product. V2 = scale and upkeep.

MVP (~72 screens)
  • Fresh-install recovery entry (Flows A/A1)
  • Preset setup — pick ONE shape, minimal edit
  • Enrollment + mandatory tests, all 4 methods (incl. the .eml help sheet)
  • Waiting period (24h floor, 48h default)
  • Recovery password + hidden values
  • Review + save · Recovery Card (card only)
  • Recovery, chapters 1–3, resumable — done-terminal without cleanup
  • Guardian approvals, manual: the checklist row shows the exact payload to sign + paste-back (no hosted page yet)
  • Cancel flow (polling banner; light "cancelled" terminal)
  • Management incl. path editing — no remove-and-recreate to change one value
V1 (~44 screens)
  • Hosted guardian page (sync; mobile, decline, offline signing)
  • Express wizard education layer (inventory → recommendation)
  • Dry run (the rehearsal)
  • Advanced builder (multiple groups, untested saves)
  • Nudge system + shield badge
  • Alerts / push notifications
  • Same-install account list (gated)
  • Deferred attack-round states (M9, M13, M16, M23, M34)
V2 (~13 screens)
  • Post-recovery cleanup (flagged methods, deferral banner)
  • Post-cancel triage
  • Apply to other accounts
  • Health checks + "Last check" stat
  • Async guardian approvals (E2) · IPFS/IPNS page hosting
  • Multichain stays out of scope
What the split accepts, said honestly

With cleanup and triage in V2, methods tied to a lost device stay live after an MVP recovery, and a cancelled attacker keeps a working method. The MVP "done" and "cancelled" screens say this and point to the MVP defenses: edit the path, remove recovery, or move funds. MVP blockers for the kit team: funding/executor (Q7/19), ZK Email relayer + prover (Q16/77), group encoding (T10), the 24h revert surface (74), and — newly MVP-blocking — value visibility / encryption scope (Q29/53).
