# Kohaku extension — Account-recovery work items

> **Status: v2 (2026-08-20)** — updated per Fibo's second review round on [PR #2](https://github.com/FiboAtWonder/kohaku-extension/pull/2). Extension-side changes needed to host the Account-recovery feature; the SDK side lives in `social-recovery-sdk-requirements.md`. Division of labor: the SDK prepares and computes; the extension signs, broadcasts, stores, and renders. Substrate (decided 2026-08-20): a **bare-bones 4337 implementation**, not the Ambire account stack — so the Ambire-specific blockers from the 2026-08-19 investigation (privilege commitments, `CALL_TO_SELF` rejection, recovery outside `validateUserOp`) no longer apply. Methods (decision 80): passkey, guardians, Anon Aadhaar, zkPassport — ZK Email is out. Milestone tags per spec decision 79.

## MVP

1. **4337 account support.** Create/deploy the bare-bones 4337 smart account and install the recovery module, driving the SDK's `prepareSetup` batch as ONE owner confirmation (Flow C step 8). Needs the account factory, counterfactual address handling, and the deploy-on-first-op path. This replaces the old Ambire-privileges route and its self-call validation problem.
2. **UserOperation submission (bundler + paymaster).** Send the SDK's prepared UserOps: bundler client, paymaster sponsorship for initiate/execute (the recovery submitter has no funded account — sponsorship is the primary path, per SDK assumption A5), status/receipt tracking. Keep a **self-pay fallback**: broadcast the prepared transaction from a funded EOA when no paymaster answers. Note the current Sepolia consts declare no bundler/paymaster/SA support (`testnetNetworks.ts`) — align them with the chosen stack (was item 9).
3. **Proving host — scoped down.** Proving in the MV3 service worker is *proven to work here*: the Railgun stack already runs Groth16 BN254 there (ark-circom + ark-groth16 + wasmer witness calculator, WASM loaded via `browser.runtime.getURL` in `background.ts:369`), kept alive by the existing keep-alive tick. So the default is: **run proofs in the service worker, behind the same single-instance WASM lock** (`railgunV2.ts:130`), with progress surfaced to the UI. An `offscreen` document is needed **only if** we later want multithreaded WASM (SharedArrayBuffer → COOP/COEP manifest keys) or hit keep-alive limits on the longest proofs. Decide after the first real zkPassport/Aadhaar proof is measured in-product.
4. **Passkey ceremonies in a full tab.** The action popup dies on focus loss and `create()` is focus-checked — a QR hand-off kills it. Run all WebAuthn in a tab/options page (works since Chrome 122; RP ID = the extension id). **Day-one test:** hybrid QR against real iOS/Android with the `chrome-extension://<id>` RP ID; fallback = a domain RP ID via host_permissions + Related Origin Requests.
5. **Method input surfaces.** Aadhaar QR **image upload** (one `react-dropzone` precedent exists — `ImportSmartAccountJsonScreen.tsx`). zkPassport's input surface (NFC scan / document photo / other) is TBD from its research pass. The `.eml` upload is dropped with ZK Email (decision 80).
6. **Recovery watcher wiring.** Poll `getPendingRecovery` (alarm/tick driven — no generic event watcher exists today) and wire results to: a new `BannerCategory` + `Action` union member (note `maxBannerCount = 1` — the pending-recovery banner must win), `browser.notifications`, and the badge (D2-01, B-03, D-13).
7. **Recovery + setup state (the SDK is stateless).** The extension owns: the setup draft, the recovery session (collected claims, resume, the decision-70 wipe triggers), and the backup set. New `StorageProps` entries + migration. Check keep-alive interplay for long proofs, and auto-lock (1-day default `chrome.alarms`) versus multi-day waiting periods.
8. **Port-messaging targeting.** `PortMessenger.send` broadcasts to every open port (`portMessenger.ts:76`); recovery secrets (proof material, approvals, passkey challenges) must be routed to their surface only.

## V1

9. **Guardian approval page.** Extension-built and extension-served at a relative path (decision 51): rendering, wallet connect (injected + WalletConnect), the offline copy/paste path, and the decline branch. It consumes exactly two SDK calls — `buildApprovalPayload` (what to sign) and `parseApproval` (signature → claim). QR display for the request link exists (`react-native-qrcode-svg`).
