# Kohaku extension — Account-recovery work items

> **Status: v4 (2026-08-24)** — updated through the fourth review round (decisions 84–89) on [PR #2](https://github.com/FiboAtWonder/kohaku-extension/pull/2). Extension-side changes needed to host the Account-recovery feature; the SDK side lives in `social-recovery-sdk-requirements.md`. Division of labor: the SDK prepares and computes structural facts; the extension signs, broadcasts, stores, renders — **and owns safety grading** (ruled 2026-08-20: the SDK serves many wallets, each with its own bar for "safe enough"). Substrate (decided 2026-08-20): a **bare-bones 4337 implementation**, not the Ambire account stack — so the Ambire-specific blockers from the 2026-08-19 investigation (privilege commitments, `CALL_TO_SELF` rejection, recovery outside `validateUserOp`) no longer apply. Methods (decision 80): passkey, guardians, Anon Aadhaar, zkPassport — ZK Email is out. Milestone tags per spec decision 79.

## MVP

1. **4337 account support — smart account at initialization is a MUST (decision 88).** The standard create flow deploys the bare-bones 4337 smart account at initialization (today the app creates a bare EOA — that changes; hard precondition for the whole feature) and installs the recovery module — while the recovery fast-track (Flow A1) creates only an EOA that is set as the signer of the recovered account — driving the SDK's `prepareSetup` batch as ONE owner confirmation (Flow C step 8). Needs the account factory, counterfactual address handling, and the deploy-on-first-op path. Two entry routes: a **freshly created account** (the demo's main flow) and **an existing EOA set as the signer** of the 4337 account — the second keeps the user's current key, so no new seed ceremony (the account address is still the 4337 account's; only recovery of an existing 4337 account leaves the address untouched, which is what decision 25's copy promises). Replaces the old Ambire-privileges route and its self-call validation problem. Also (88): when a recovery is started from an EXISTING account, nothing is created or merged — that account's key becomes a signer of the recovered account too, and the logged-in entry must say "this account's key now controls two accounts".
2. **Recovery submission + gas-deposit screens (decision 87).** MVP is user-funded: broadcast the SDK's PreparedTx from the recoverer's key, with two gas-deposit surfaces — onboarding (A1-04, also in the standard create flow) and pre-submit (D-09) — each auto-skipped when the account already holds enough (needs a balance-vs-estimated-cost check). Contract side, `execute` reimburses `msg.sender` (may change). Bundler + paymaster sponsorship moves to **V1**; who operates the paymaster is open. Align the Sepolia consts (`testnetNetworks.ts`) with the chosen stack.
3. **Proving host (we host it; the SDK does the proving).** The prover ships in the SDK behind one call — we only choose the JavaScript context it runs in. Proving in the MV3 service worker is *proven to work here*: the Railgun stack already runs Groth16 BN254 there (ark-circom + ark-groth16 + wasmer witness calculator, WASM loaded via `browser.runtime.getURL` in `background.ts:369`), kept alive by the existing keep-alive tick. So the default is: **run proofs in the service worker, behind the same single-instance WASM lock** (`railgunV2.ts:130`), with progress surfaced to the UI. An `offscreen` document is needed **only if** we later want multithreaded WASM (SharedArrayBuffer → COOP/COEP manifest keys) or hit keep-alive limits on the longest proofs. Decide after the first real zkPassport/Aadhaar proof is measured in-product.
4. **Passkey ceremonies in a full tab.** The action popup dies on focus loss and `create()` is focus-checked — a QR hand-off kills it. Run all WebAuthn in a tab/options page (works since Chrome 122; RP ID = the extension id). **Day-one test:** hybrid QR against real iOS/Android with the `chrome-extension://<id>` RP ID; fallback = a domain RP ID via host_permissions + Related Origin Requests.
5. **Method input surfaces.** Aadhaar QR **image upload** (one `react-dropzone` precedent exists — `ImportSmartAccountJsonScreen.tsx`). zkPassport's input surface (NFC scan / document photo / other) is TBD from its research pass. The `.eml` upload is dropped with ZK Email (decision 80).
6. **Recovery watcher wiring.** Poll `getPendingRecovery` (alarm/tick driven — no generic event watcher exists today) and wire results to: a new `BannerCategory` + `Action` union member (note `maxBannerCount = 1` — the pending-recovery banner must win), `browser.notifications`, and the badge (D2-01, B-03, D-13).
7. **Recovery + setup state (the SDK is stateless).** The extension owns: the setup draft, the recovery session (collected claims, resume, the decision-70 wipe triggers), and the backup set. New `StorageProps` entries + migration. Check keep-alive interplay for long proofs, and auto-lock (1-day default `chrome.alarms`) versus multi-day waiting periods.
8. **Port-messaging targeting.** `PortMessenger.send` broadcasts to every open port (`portMessenger.ts:76`); recovery secrets (proof material, approvals, passkey challenges) must be routed to their surface only.

## V1

9. **Guardian approval page.** Extension-built and extension-served at a relative path (decision 51): rendering, wallet connect (injected + WalletConnect), the offline copy/paste path, and the decline branch. It consumes exactly two SDK calls — `buildApprovalPayload` (what to sign) and `parseApproval` (signature → claim). QR display for the request link exists (`react-native-qrcode-svg`).
10. **Alerts opt-in surface** (C-08) wired to the watcher; push/system notifications degrade per decision 11.

## V2

11. **Fragility grading + the graded meter (decision 86).** The SDK returns path and method metadata but no verdict — we implement the rules (single trust root, same-seed guardians, minimum availability, device-bound-only floors), the grade and the graded "Recovery ready" meter + honesty copy. MVP/V1 show a plain set-up/not-set-up status line instead. Inputs: SDK metadata plus wallet-held knowledge (seeds for the same-seed check).
12. **Apply-to-others iteration UI** (C-09 family) over the SDK's per-account prepare calls, with per-account progress (decision 72).
13. **Health-check scheduling** (Flow F): the passkey check is a **user-gesture test by design** (ruled 2026-08-20) — we prompt, the user taps, we record the result; background runs cover only what needs no interaction, and their failures render as "unproven". Meter + "Last check" stat (decision 71).
