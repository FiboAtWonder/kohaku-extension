# Kohaku extension — Account-recovery work items

> **Status: v6.** Extension-side changes needed to host the Account-recovery feature; the SDK prepares and computes, the extension signs, broadcasts, stores, renders and owns safety grading; SDK side: `social-recovery-sdk-requirements.md`; milestone tags per decision 79. Version history: `social-recovery-ux-status.md`.

## MVP

1. **4337 account support — smart account at initialization is a MUST (decision 88).** The standard create flow deploys the bare-bones 4337 smart account at initialization (today the app creates a bare EOA — that changes; hard precondition for the whole feature) and installs the recovery module — **the account's 7579 recovery adapter comes from the kit team** (SDK or contracts side), not from us: we ship no Solidity, so this item is integration and wiring only (REC-20) — while the recovery fast-track (Flow A1) creates only an EOA that is set as the signer of the recovered account — driving the SDK's `prepareSetup` batch as ONE owner confirmation (Flow C step 8). Needs the account factory, counterfactual address handling, and the deploy-on-first-op path. Two entry routes: a **freshly created account** (the demo's main flow) and **an existing EOA set as the signer** of the 4337 account — the second keeps the user's current key, so no new seed ceremony (the account address is still the 4337 account's; only recovery of an existing 4337 account leaves the address untouched, which is what decision 25's copy promises). Replaces the old Ambire-privileges route and its self-call validation problem. Also (88): when a recovery is started from an EXISTING account, nothing is created or merged — that account's key becomes a signer of the recovered account too, and the logged-in entry must say "this account's key now controls two accounts".
2. **Recovery submission + gas-deposit screens (decision 87).** MVP is user-funded: broadcast the SDK's PreparedTx from the recoverer's key, with two gas-deposit surfaces — onboarding (A1-04, also in the standard create flow) and pre-submit (D-09) — each auto-skipped when the account already holds enough (needs a balance-vs-estimated-cost check). Contract side, `execute` reimburses `msg.sender` (may change). Bundler + paymaster sponsorship moves to **V1**; who operates the paymaster is open. Align the Sepolia consts (`testnetNetworks.ts`) with the chosen stack.
3. **Proving host (we host it; the SDK does the proving).** The prover ships in the SDK behind one call — we only choose the JavaScript context it runs in. Proving in the MV3 service worker is *proven to work here*: the Railgun stack already runs Groth16 BN254 there (ark-circom + ark-groth16 + wasmer witness calculator, WASM loaded via `browser.runtime.getURL` in `background.ts:369`), kept alive by the existing keep-alive tick. So the default is: **run proofs in the service worker, behind the same single-instance WASM lock** (`railgunV2.ts:130`), with progress surfaced to the UI. An `offscreen` document is needed **only if** we later want multithreaded WASM (SharedArrayBuffer → COOP/COEP manifest keys) or hit keep-alive limits on the longest proofs. Decide after the first real zkPassport/Aadhaar proof is measured in-product.
4. **Passkey ceremonies in a full tab.** The action popup dies on focus loss and `create()` is focus-checked — a QR hand-off kills it. Run all WebAuthn in a tab/options page (works since Chrome 122; RP ID = the extension id). **Day-one test:** hybrid QR against real iOS/Android with the `chrome-extension://<id>` RP ID; fallback = a domain RP ID via host_permissions + Related Origin Requests.
5. **Method input surfaces.** Aadhaar QR **image upload** (one `react-dropzone` precedent exists — `ImportSmartAccountJsonScreen.tsx`). zkPassport's input surface (NFC scan / document photo / other) is TBD from its research pass. The `.eml` upload is dropped with ZK Email (decision 80).
6. **Recovery watcher — we own the whole thing (REC-41, open).** The kit ships **NO reference watcher**: their spec calls the watcher "a role rather than a service the kit builds", so the entire event-reader is ours, not just the wiring. Poll `getPendingRecovery` (alarm/tick driven — no generic event watcher exists today) and wire results to: a new `BannerCategory` + `Action` union member (note `maxBannerCount = 1` — the pending-recovery banner must win), `browser.notifications`, and the badge (D2-01, B-03, D-13). **Unresolved:** at the private levels the wait and the finalize deadline may have **no chain source at all** — the wait lives inside the setup commitment and the attempt event may not carry it in the clear — so there may be nothing for a watcher to count down from. Ask pending in `social-recovery-kit-asks.md`; with no floor under the wait (decision 85), the MVP alerting-honesty line is load-bearing until it is answered.
7. **Recovery + setup state (the SDK is stateless).** The extension owns: the setup draft, the recovery session (collected claims, resume, the decision-70 wipe triggers), and the backup set. New `StorageProps` entries + migration. Check keep-alive interplay for long proofs, and auto-lock (1-day default `chrome.alarms`) versus multi-day waiting periods. Two shapes the storage must carry: the stored recovery session **keeps the predicted `attemptId` beside the claims**, or a resume cannot tell a void claim from a valid one (REC-27); and **collecting, storing and re-importing the backup set is ours** — the SDK only packs and unpacks the bundle format (`packBackupSet` / `unpackBackupSet`), so the secrets themselves live in our storage.
8. **Port-messaging targeting.** `PortMessenger.send` broadcasts to every open port (`portMessenger.ts:76`); recovery secrets (proof material, approvals, passkey challenges) must be routed to their surface only.
9. **Colibri `p256verify` gap — ours, not a kit ask.** Passkey verification calls the P-256 precompile, which sits outside Colibri's proof coverage, so verified reads fall back to unverified RPC (`ColibriRpcProvider.ts:43`) and the "Verified by Colibri" badge overstates them. This is a Kohaku RPC-stack issue, not a kit ask — fix the badge's honesty here, and route the coverage question inside Kohaku.
